# Test vectors

Read the files in this order:

| File | Cases | Purpose |
| --- | --- | --- |
| [keygen.json](keygen.json) | 6 valid, 1 invalid | Construction, TapTweak, shares, and reconstruction |
| [validation.json](validation.json) | 10 invalid | Parameters, secret scalar encodings, and commitments |
| [acceptance.json](acceptance.json) | 1 valid base, 4 shared encodings, 10 invalid replacements | Participant checks and binding A0/A1 to commitments |

This organization follows the operation-specific files and shared inputs in
[BIP 327](https://github.com/bitcoin/bips/tree/master/bip-0327/vectors).
As in [BIP 340](https://github.com/bitcoin/bips/blob/master/bip-0340/test-vectors.csv),
each failure targets a distinct condition. Repeated empty/short/long variants
and duplicate successful setups have been removed.

## Key generation

Each case provides `inputs.n` and initial `inputs.coefficients` in ascending
coefficient order. The threshold is the coefficient count. `expected` records
the tweak, final coefficients, both public keys, serialized final commitment,
and shares indexed by zero-based `id`. Scalars are 32-byte big-endian hex;
points and commitments use the encodings in the BIP.

| Valid case | Reason to keep it |
| --- | --- |
| `bip341_1_of_1` | Published BIP 341 no-script-path expectations; minimum setup and imported secret |
| `even_y_2_of_3` | Ordinary threshold setup; all three signing subsets |
| `odd_y_3_of_3` | Only the constant is normalized; zero leading coefficient and infinity nonconstant commitment; t = n |
| `equal_commitments` | Equal nonconstant commitments are valid distinct slots; nonzero quadratic term |
| `zero_initial_share` | A zero initial share is allowed if its final share is nonzero |
| `maximum_participants` | n = 128 and identifiers at both ends of the range |

The first case pins the scalar input, tweak, final scalar, and key X coordinates
from `scriptPubKey[0]` and `keyPathSpending[0].inputSpending[0]` in the linked
BIP 341 source; compressed prefixes reflect the corresponding points' parity.
Other cases are generated by the reference implementation. The runner also
checks the constant-only transformation, evaluates every share using a power
sum independently of Horner's method, and reconstructs both the secret and
public key from threshold subsets.

The 128-participant case lists only shares 0 and 127 and three
`reconstruction_subsets`. Every share is still checked by the runner. Other
cases list every share and check all threshold subsets. Initial and final
commitment arrays are not duplicated: derive them by multiplying each
coefficient by G; the serialized final commitment is provided explicitly.

The error case must fail with a zero final share. Retry behavior is tested
separately using controlled randomness.

## Input validation

All cases must be rejected (`False` for `VerifySecShare`, failure otherwise):

- `parameter_error_cases`: apply `(t, n)` to generation (both generated and
  imported secrets), public-share derivation, share verification, and
  participant acceptance. The runner also checks the parameter and identifier
  helpers where applicable.
- `scalar_error_cases`: use `value` as an imported secret or a participant's
  final secret share. The cases distinguish length, zero, and the group-order
  boundary. The zero case also checks the internal generator's constant term.
- `commitment_error_cases`: parse `value` as a commitment with threshold `t`,
  and use it in derivation, verification, and acceptance. The cases distinguish
  length, an infinity constant, and an invalid point prefix.

Other acceptance inputs come from the valid base. For parameter failures with
threshold 0 or 1, the runner uses the 1-of-1 key material to avoid an unrelated
commitment-length failure for threshold 1.

## Participant acceptance

`base` is a complete valid input. It must succeed with the supplied `pubshares`
and with `pubshares` omitted or `null`. Hex strings encode bytes; `id` maps to
Python's `participant_id`.

Each `error_test_cases` entry replaces the named top-level fields in a fresh
copy of `base`. Arrays are replaced in full. `expected_failure` describes the
reason for rejection, not required exception wording.

Each `point_encoding_error_cases` value is applied independently to
`original_pk`, `thresh_pk`, and `pubshares[1]`, leaving other inputs unchanged.
All three applications must fail. The padded point encodes the valid public
share at index 1, so accepting that encoding would expose a length-check bug.
The runner repeats acceptance failures under `python -O` to check that parsing
does not depend on assertions.

Exceptional tweak hashes and random-sampling retries remain in the small
mock-based Python tests. See the [repository README](../README.md#test-vectors)
for regeneration and test commands.
